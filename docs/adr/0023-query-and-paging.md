# ADR-0023 查询与分页是参数，不是另一个方法，也不是开关

来源：用户裁定（「分页和 query 可能都要做，很多搜索的方法可能都要有」「分页要不要做成开关？还是一个方法，靠参数不同走不同结果？」2026-10-31）；具体算子、字段白名单的来源、放置层次由实现默认补充。

## 一个方法，靠参数

`platform_call` 只有**一个**方法，分页和查询都是它的可选参数：

```
platform_call({ method, params, limit?, offset?, where?, fields?, order_by?, group_by? })
```

不拆成 `platform_call` + `platform_query` 两个。理由跟 ADR-0020 里「平台能力固定占 2 个工具位」是同一条：**工具表每一轮都进上下文**。多一个工具位不是多一行文档，是每一次调用都要多一次「我该用哪个」的判断——而这两个动作用的是同一份权限、同一个白名单、同一份结果，拆开只会让模型在两个等价的东西之间犹豫。

也不拆成「读方法」和「写方法」两套 API：`message.forward_content` 既是读也是写不了，分不分都取决于平台，桥不该替平台决定。

## 分页不是开关

**不做 `paginate: true/false`。** 分页是默认行为，而且**不需要时看不见**：

- 结果装得下（≤ 24 KiB、≤ limit 条）→ 返回原样，`_page` 里 `total == returned`、`has_more == false`；
- 装不下 → 自动按条切，`_page` 告诉你 `total` / `next_offset`。

想要「一次全给」就把 `limit` 调大（上限 500）。这本身就是开关，而且是**有上限的开关**——布尔开关的问题是它可以被设成「给我一兆」，那正好是这套机制要防的事。

另一个理由更实际：一个布尔开关意味着两条渲染路径。两条路径就是两份 bug，而其中一条（`paginate:false`）只在「结果特别大」时才走到——也就是最难测、最容易崩的那条。

`platform_call` 的 `_page` 总是存在（哪怕只有 3 条：`total:3, returned:3`）。这不是噪音，是回答问题：**agent 分不清「一共 3 个」和「被截到 3 个」，除非桥直接告诉它。**

## 查询：桥做，不是平台做

`where` / `fields` / `order_by` / `group_by` 全部在**桥这一层**执行，作用在平台返回的 JSON 数组上：

- 平台方法签名一个都不用改（五十个方法，改一遍就是五十处适配器改动）；
- 任何平台的任何列表都自动可用（成员、好友、群、转发正文），不必为每个方法写一遍；
- 不会因为某个平台不支持 `where` 就退化成「拉全表」。

**字段白名单从数据里推**：取这批条目的顶层键（并集）当合法字段。写死的表在平台加字段那天就过期；推出来的表永远和这次的数据一致。传错字段照样报错，并且把真实可用的字段列出来——这是 agent 一轮就能改对的关键：

```
[bad_field] 没有字段 rol；这批数据里有的字段：user_id / nickname / role / join_time
```

字段路径支持 `sender.id`、`members.0.name`。投影（`fields`）会把路径还原成嵌套结构。

## 算子只有九个

`eq` `ne` `in` `gt` `gte` `lt` `lte` `contains` `not_null`。够了。每多一个算子，模型就多一个记错的概率，而「查一下」这件事本身没有那么多花样。

`contains` 在对象上会看**所有字符串字段**：模型不用知道「这句话是嵌在 `data.list[].message[].text` 的哪一层」——它只要说「含这个词」。

## group_by 是性价比最高的那一格

「群里几个管理员」不该需要拉全表。给 `group_by: "role"`，返回：

```json
{"matched": 213, "group_by": "role",
 "groups": [{"key": "member", "count": 206}, {"key": "admin", "count": 7}]}
```

213 人、7 个管理员，一次调用、一百来个字节。`matched` 是过滤之后的总数，`groups` 按条数从多到少排（同数按名字，保证同样输入同样输出）。

分组时不切页：分组结果本来就只有十几行。

## 顺序：过滤 → 分组/排序 → 投影 → 分页

顺序错了数就不对：先分页再过滤，`_page.total` 给的是过滤前的数，模型永远算不出「到底几个」。所以 `apply_to_value` 在 `slice` **之前**执行，这一条写在代码注释里，也写在这里。

## 还没做的

- **`get_history` 的文本检索**：语料是流水，`where` 里想按「消息正文含某词」查，需要一个投影时补上、输出时剥掉的 `text` 派生字段，不然要么污染输出、要么过滤不到。做法清楚，但这一批不做——现在的 `get_history` 已经有 `before` + `limit` + `columns`，够翻上下文。
- **`aggregate`（sum/avg/min/max）**：现在的真实需求只有计数，加了也没人用，先留着。
- **跨方法统一的分页游标**：现在是 offset（平台结果）+ before（流水）两种。统一成不透明 cursor 更好看，但也更难点开看——流水用编号翻页本来就是最稳的，没必要为了对称牺牲它。
