# ADR-0021 agent 反馈通道：写建议，不是填表

来源：用户裁定（「希望做一个反馈功能接口，便于 agent 进行反馈」「反馈接口是给 agent 写建议，不是填表，可以贴出处编号、能表示出现次数，这样设计者才有 actionable 的东西」2026-10-31）；字段尺寸、去重、生命周期、权限窗口由实现默认补充，可推翻。

## 那条痛点从哪来

agent 卡住的时候，桥没有给它任何正式出口。它能做的只有三件事：反复重试注定失败的调用、换条路硬凑、或者干脆绕过桥去戳平台端口（真机上发生过：直连 `127.0.0.1:53000` 调 OneBot）。绕道没有订阅校验、没有审计、没人知道它撞了什么墙。

所以反馈通道不只是「收集意见」。它首先是一条**受控的出口**：让「我这儿缺东西」这句话有个地方去，绕道的动因才消失。这也是它必须有结构的原因——一句「不好用」处理不了，一条「`get_group_member_list` 在 24 人的群里只回来 16 个，没有 total，出处 #620」才能动手。

## 形状：一个正文框

`report_feedback` 只有一个必填字段 `text`。第一行当标题，其余当正文。想写多长写多长（上限内），不用挑分类、不用想严重程度。

```json
{
  "text": "platform_call 调 group.get_member_list，24 人的群只回来 16 个，没有 total，我无法判断 15 个管理员是不是完整数字。\n第 2 次撞到了。",
  "refs": ["#620", "group.get_member_list", "platform_call"],
  "count": 2,
  "kind": "gap",
  "suggestion": "列表结果统一带 total / has_more"
}
```

为什么不做成表单（kind + severity + title + detail + repro + expected…）：**填表会劝退**。模型的注意力是有限的，一处卡住时让它先做五个选择题，它多半就放弃了，或者瞎填一遍——瞎填的分类比没有分类更麻烦，因为它看起来像数据。

结构化字段全部可选，缺省值有明确来源：

| 字段 | 必填 | 缺省 | 上限 |
|---|---|---|---|
| `text` | ✅ | — | 4000 字（超出截断并回告） |
| 标题（正文第一行） | 自动 | 第一行非空文本 | 120 字 |
| `refs` | — | 空 | 20 条，每条 120 字 |
| `count`（自称撞了几次） | — | 1 | 100000 |
| `kind` | — | `friction` | bug / gap / friction / idea |
| `severity` | — | bug、gap → `major`；其余 → `minor` | blocker / major / minor |
| `suggestion` | — | 空 | 1000 字 |
| `tool` | — | 空 | — |

现场（谁提的、哪个会话、哪个 harness、哪个房间、哪张票、什么模型、这一轮还在不在跑）**由桥自己补**，不让 agent 抄一遍——抄的东西会写错，而且它抄的时候还得花 token。

## refs 是这个设计的重点

「出处编号」不是附属信息，它是**可复现性**。有 `#620` 就能去流水里翻那条消息、看那一轮投了什么；没有编号的反馈只能当印象处理。所以：

- 工具描述里明确写着「有编号的反馈才能被复现，没编号的只能被当成印象」。
- `refs` 不校验真实性——有时候最该记下来的正是「那个编号查不到」。
- `count` 同理：`3 次` 和 `1 次` 在排序上是两件事，用户拿到的那张痛点表就是按「真实发生频率」排的。不说次数，反馈就只能按到达时间排。

## 怎么存

一张表，`feedback`（库 schema 7）：

| 列 | 说明 |
|---|---|
| `id` | 自增，永不复用 |
| `fingerprint` | 去重指纹 = FNV-1a(归一化标题)，唯一索引 |
| `title` / `body` / `suggestion` | 正文三段 |
| `kind` / `severity` | 分类与影响 |
| `refs` | JSON 数组 |
| `occurrences` | agent 自称发生次数（每次报告相加） |
| `repeats` | 被报告了几次（桥自己数） |
| `tool` / `session` / `harness` / `room` | 哪儿的事 |
| `context` | 现场 JSON：票、模型、这一轮是否还在跑、时间 |
| `status` / `note` | open / acked / resolved / wontfix + 处理备注 |
| `first_at` / `last_at` | 第一次、最近一次 |

**一次反馈最大多大**：正文 4000 字 + 建议 1000 + 出处 20×120 ≈ 一次性上限约 8 KB（中文按 3 字节算，24 KB 上下）。正常一条在 200 字节到 2 KB 之间。

**整表多大**：上限 5000 条（`FEEDBACK_CAP`），超出按 `last_at` 删最久没被提过的。5000 × 平均 500 字节 ≈ 2.5 MB，最坏（全塞满）约 100 MB 但不可能出现——上限是按字符算的，真要塞满得每条都写到上限，那时人也该处理了。

为什么不落文件：反馈要被查询（按状态、按次数排序）、要被改状态（处理完标掉），这两件事 SQLite 比一堆 JSON 文件省事得多，而且它跟着状态库一起备份。

## 去重与「又出现了」

指纹相同 → 合并：`repeats + 1`、`occurrences += count`、`last_at` 刷新。**如果原来是 resolved / wontfix，状态退回 open**——它又出现了，说明没修好。这一条比任何「重新打开」按钮都准：复发是事实，不是意见。

指纹只在**标题**上算，不算类型、不算正文。同一个坑这次报 gap、下次报 bug，还是同一个坑——合并时保留第一次的类型（人已经看过那一行，不该被后来的报告悄悄改分类）。换个说法重提会变成两条——这是**故意**的取舍：错分成两条只是列表长一点，错合成一条会丢信息。

## 权限窗口：反馈不跟着轮次死

轮次结束、票作废之后，仍有一个宽限窗（10 分钟）：

- `ack_messages` 可用 **60 秒**（补确认，见 ADR-0010 修订）；
- `report_feedback` 可用 **整个 10 分钟**。

理由不同：确认绑定的是「这一轮你处理到哪」，时间越久越说不清；而反馈是「刚才发生了什么」，收工后想起来完全正常——恰恰是收工后才最容易想清楚「我为什么卡住」。其余工具在轮次结束后一律 `no_active_round`，文案明说「这一轮不会再有工具可用，请结束本轮」，避免 agent 继续撞。

## 人怎么看到

- 桥日志一行：`反馈 #12 [gap major] main：platform_call 少了 total（自称 3 次，第 1 次报告）`。
- 控制台 `GET /api/feedback?status=open&limit=20`（带 token）。
- 控制台 `POST /api/feedback/:id/status`，body `{"status":"resolved","note":"已按 ADR-0022 修"}`。

只进不出会变成垃圾场，所以「改状态」是这套设计的一部分，不是可选项。

## 不这样会怎样

- 只做自由文本、不存结构：看的人得逐条读，读第三条就放弃了。
- 存结构但不存次数：没法排序，最后按到达时间处理，最烦的那个坑可能排在第二十条。
- 反馈跟着轮次死：最想说话的时刻（这一轮干什么都不成）恰好说不了话。
- 不做去重：同一个坑被十个会话各提一次，看起来像十个问题。

## 还没做（明确留白）

- 反馈不回流给 agent：`report_feedback` 只写不读，agent 看不到「你提的这条已经修了」。等有了「版本」概念再说——现在桥没有版本号，回来也说不清修的是哪个版本。
- 不自动附带工具调用轨迹：只存 refs 和现场。要做的话得先想清楚脱敏（会话内容不该整段进反馈表）。
