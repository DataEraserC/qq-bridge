# ADR-0014 状态落盘：一个 SQLite 文件装下桥记得的所有事

来源：**用 SQLite 落盘是用户裁定**（选了「先把 SQLite 落地」）。下面这些具体做法——
存哪几样、表怎么切、路径默认值、版本怎么管——都是实现默认，随时可推翻。

## 这条决定了什么行为

- 桥重启之后接着上次的账做：**编号不重数、水位不回零、笔记还在、「第 N 次投递」的 N
  接着数**。
- 存四样东西：流水（记录）、水位、投递次数、笔记。加一个结构版本号。
- 存的位置默认 `state/qqab.db`，配置里 `[storage] path` 可改。目录不存在会自动建。
- 库打不开、或者库的结构版本比程序新，**启动就失败**，不往下走。
- 票和排队中的轮次**不落盘**。重启后旧票全废，等下一次唤醒重新开轮。

## 不这样会怎样

内存实现下，每重启一次就失忆一次：群聊编号从 #1 重来、`get_history` 看不到重启前的、
笔记全丢、没确认的消息看着像从没投过。这些不是「不方便」，是**错的**——它们让 agent
看到的世界和真实发生的事对不上，而且错得很安静：桥照常运行，只是账目突然清算归零。

更要紧的是它挡住了后面的验证：多轮行为、重投、水位连续性，都得跨进程才能验。越晚做
越贵。

## 技术细节

- `Store` 保持为一组 trait（`Transcript` + `Watermarks` + `Notes` + `Deliveries`），
  两份实现：`MemoryStore`（测试、嵌入式）与 `SqliteStore`（正式跑）。调度层只认 trait，
  换后端不动调度。
- 投递次数从「桥的内存字段」搬进存储：它原来是 `Bridge` 里一个 `HashMap`，重启即失效。
  既然要给用户「重启后 N 接着数」，它就得和记录同寿命。
- 编号用「`MAX(record_id) + 1` 在事务里算」而不是自增计数表：编号本来就是房间内的，
  一张表里天然就是这么切的。单写者（一把互斥锁）保证不会撞。
- 确认走事务：先整批校验编号是否存在，**有任何一个不存在就整批拒绝**，避免「写了一半」。
  水位推进是「从当前水位往上逐个数，遇到缺口停」——和内存实现的语义逐字对齐。
- 开 WAL（`journal_mode=WAL`）：读不被写挡住。内存库跳过。`synchronous=NORMAL` 是
  可接受的折中：断电最多丢最后几条记录，不会把库写坏。
- `meta.schema_version` 现在写 1。版本对不上就拒绝打开：老程序往新结构里写，比起不来
  严重得多。改表必须先写迁移。
- 依赖 `rusqlite` 的 `bundled` 特性：把 SQLite 源码一起编进去，不依赖系统装的
  `libsqlite3`，换机器不会因为库版本不同出现诡异行为。
- 已知没做：流水不自动清理（会一直长）、不做加密、不支持两个进程开同一个库。
