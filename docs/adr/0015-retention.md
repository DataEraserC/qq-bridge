# ADR-0015 流水保留：只削读过的，按条数和天数两个上限

来源：**「清理做成策略、跟着配置走」是用户裁定**（按天数 / 按条数 / 不清理，用户明确要
这三选）。下面这些具体数值与做法是**实现默认**，可推翻：默认 5000 条 / 90 天、只考虑在册
订阅者、每房间至少留一条、5 分钟扫一次。

## 这条决定了什么行为

- 流水有了上限，不再是只增不减。超出的部分被删掉，库文件不会无限长。
- **只删已经读过的**。任何在册订阅者还没读到的记录，一条都不删——它们还是下一轮的投递原料。
- 判据三条，同时成立才删：编号低于安全线、不在最新 N 条里、时间早于时间线。
- 两项配成 0 就是完全不清理。默认是 5000 条 / 90 天。
- 删了不影响编号：删掉 1..1200 之后，下一句仍然是 1201。
- 真删了会打一行日志；没删就不吭声。

## 不这样会怎样

两条路都走过一遍：

**不清理。** 一个群一天几百条，一年就是十几万条记录，加上元素 JSON，库会长到几百 MB。
`get_history` 每次都要在越来越大的表里翻，备份越来越慢。这不紧急，但会一直变糟。

**不看水位就清。** 这是真会出事的版本：删掉某条还没投出去的消息，agent 就永远看不到它了，
而且没有任何迹象——水位照样往前推，未读列表里就是少了一条。所以「读没读过」必须是第一
判据，比条数和天数都优先。

还有一条更隐蔽的坑：**把房间删空**。编号靠 `MAX(record_id)+1` 推，一条不剩时下一个又回到 1，
而那个设备的水位还停在 1200。新消息编号 1 ≤ 水位 1200，于是**被当成已读**：消息收下来了、
记进库了，但永远不进未读、永远不会投给 agent。所以每个房间至少留一条，作为编号基准。

## 技术细节

- 判据由调度层算好（它才看得见配置和水位），存储层只负责按判据执行：
  `Transcript::prune(room, &PrunePlan { below, keep_newest, older_than })`。
- 安全线取**所有在册订阅者水位的最小值**，不是平均值也不是最大值。两个设备订同一个群时，
  快的那个不能替慢的那个做主。
- 设备从配置里删掉之后，它的水位不再参与计算：否则一个早就废弃的设备会把整个房间的历史
  永久钉住，清理形同虚设。代价是那个设备以后加回来时，中间那段它看不到。
- 没人订阅的房间直接跳过。判据（谁在读）对它们不成立，也不该由这里替人决定删什么。
- 删记录的同时清掉指向它的 `deliveries`（计数没意义了）与 `acks`（前面那条没了，前沿永远
  等不到它，留着只是让水位卡死）。
- 执行放在删除线程里，不在 `end_turn` 里做：清理和收发走同一把锁，但触发时机与轮次无关。
  桥启动先扫一次，之后每 5 分钟一次（`PRUNE_EVERY`，实现默认，暂时不做成配置项）。
- 只支持「按房间整段削」。要做「留最近 N 天但保留某几条」这种例外规则，去备份库文件，
  不要往桥里塞规则。
- 已知没做：清理不压缩库文件（`VACUUM`）。SQLite 删除后空间会留在文件里复用，文件不会
  自动变小；要缩小得手动 `VACUUM`。
