# 笔记是带主键的结构化记录，不用检索系统

笔记是内核按主键保存的长期知识，主键是「类型 + 键」：词条按词、群友按 QQ 号、话题按话题名。写入只发生在对话内，由 agent 通过 `note` 工具完成；读取分两段，一段是每回合自动注入的摘要，一段是按需查询。没有后台学习会话，没有状态机，没有检索层。

## 理由

旧实现把「学习」做成一个后台会话：抽取候选、联网搜索确认、写入 JSON、等人确认，条目带 `candidate` / `confirmed` / `rejected` 三态。这条路有四个代价，且都不是实现细节问题：

1. **最可靠的信号拿不到。** 一条群内用语最可信的确认，是 agent 用错了、被人当场纠正的那一刻。那一刻在对话里，后台会话结构上看不到它。
2. **上下文被截断。** 后台会话只看一个消息窗口，不知道当时在聊什么，抽出的词条经常脱离语境。
3. **两个写者带来全部复杂度。** 存储层要处理并发写、解析失败隔离（`.corrupt-` 备份）、限频、以及「正在研究的条目」集合。这些复杂度没有一条来自「学习」本身，全部来自「后台任务和前台 agent 同时写一个文件」。
4. **每个词两次模型调用加一次搜索**，成本高于它带来的收益。

单写者把这四条一起消掉：写入就在对话里，信号最全、上下文最新、没有并发，成本是一次工具调用。

## 为什么不用向量检索

检索系统的前提是三条：语料远大于上下文、只有一小部分与当前查询相关、相关性是语义相似。这三条在这个场景里都不成立：

- 笔记规模是几百条、不到 1 MB，全量塞进上下文都嫌少。
- 群内用语对每条消息都同等相关，不存在「检索出相关的几条」这回事。
- 键是**精确主键**（词、QQ 号、话题名），不是语义相似。

第三条是决定性的。同一个人第二次解释「67」时，要做的是**覆盖写**，不是「再追加一条近似向量」。向量库天然是追加式的，在这一步只会越存越多、越检索越乱。

## 为什么不用 Elasticsearch

为一个几百 KB 的词典起一个 JVM 服务。这与「协议用 Unix socket 是因为零端口占用」是同一类判断：引入的重量必须换来对应的能力，这里没有换来任何东西。

## 为什么不用自由文本

一份 Markdown 笔记只能全量注入，token 预算不可控；也无法按「当前范围里出现过的群友」这类条件过滤。自由文本适合人写给人看，这里需要机器按主键读写。

## 后果

- 写入成本降到一次工具调用。准确性依赖提示词与 agent 的判断，不再依赖后台抽取的质量。
- 不再需要「候选 / 已确认 / 已拒绝」状态机：不认识就不写，写错了就被纠正后覆盖。
- 每记忆一份记录，单写者，不需要文件锁——串行队列已经保证同一记忆名的回合不并发。
- 新增两样东西：`note` 工具，以及投递时的笔记摘要字段。
- 笔记属于记忆名而不是设备。两个设备共享一个记忆名，就共享一份笔记。
