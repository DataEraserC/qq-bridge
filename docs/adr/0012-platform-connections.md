# ADR-0012 平台连接：一个平台一个适配器，出站按平台分发

来源：实现默认。整体方向（要先做 QQ、OneBot 是第一个协议）来自用户裁定；下面这些具体做法
都没有经过用户拍板，随时可推翻。

## 这条决定了什么行为

- 配置里可以写多个适配器，一个平台一个：`platform`（跟房间前缀一致）、`kind`（协议种类）、
  `url`（连到哪）。
- 桥持有**一组**出站通道，按房间的平台名分发：发往 `qq:group/123` 就交给 QQ 的适配器，
  发往 `discord:...` 就交给 Discord 的适配器。
- 某个平台没接适配器，发消息会明确报错「没有为平台 X 接上适配器」，不静默丢。
- 一个平台配两个适配器、种类写错、地址不是 `ws://`，都在启动时报错，不带病运行。
- 适配器只负责自己的平台。别平台的房间递进来，它直接拒——这样「配错了」会当场暴露，
  而不是发到一个莫名的地方去。

## 不这样会怎样

如果桥只挂一个出站实现（第一版就是这样），那「一个设备同时订 QQ 群和 Discord 频道」
这个已经写进愿景的用法根本跑不起来：往 Discord 频道发的东西会走 QQ 的发送逻辑。等第二个
平台接进来才改，会把发送路径、工具面、测试全部返工一次。现在改只多一层很薄的分发。

## 技术细节

- `Outbound` trait 不变（`send(device, room, account, elements)`），`Outbounds` 包一层
  `HashMap<平台名, Box<dyn Outbound>>`，按 `room.platform` 查表。
- 连接方式选**正向 WebSocket**（桥当客户端去连 OneBot 的 WS 服务端）。反向 WS 要桥自带
  WS 服务端，多一层监听与鉴权；正向只要一个地址。真需要反向，加一种 `kind` 即可。
- 每条连接一个守护线程：连不上每 5 秒重试，断了自动重连，进程不退出。
- 一个线程同时管读和写：读带 20ms 超时，超时只是「这会儿没消息」，回头把排队的动作写出去。
  这样不需要拆 socket，也不会出现「读阻塞导致回复发不出去」。
- 写动作走队列，由同一个线程按 `echo` 配对回包——写和读永远只有一个执行者，不会串字节。
- 往桥里喂事件用 `try_lock`：桥的锁可能正被回合线程拿着（它正在等平台回话）。抢不到就
  先攒着，绝不在等锁的时候卡住写动作，否则两个方向互相等死。
- 依赖 `tungstenite`（阻塞式 WebSocket，无异步运行时），与「单进程、每连接一线程」的
  并发模型一致。
