# ADR-0012 连接：一条管道一个有名字的对象，出站按连接分发

来源：**用户裁定**（2026-10-29）——「连接」是独立对象，有适配器种类和连接信息，同一平台可以
有多条；「订阅」写的是「连接 + 房间」，不是「平台 + 房间号」。这条 ADR 覆盖了早先的
「一个平台只能配一个适配器」——那个做法是**实现默认**，不是用户拍板的东西，已作废。

## 这条决定了什么行为

- 配置里连接是一等对象，一段一条：

  ```toml
  [[connections]]
  id = "qq2"              # 连接的唯一名字，房间和订阅都靠它引用
  platform = "qq"         # 属于哪个平台（日志、显示、平台特有内容用）
  kind = "onebot11"       # 用哪个适配器
  transport = "ws-client" # 连接方向：桥主动去连
  url = "ws://127.0.0.1:3002"
  account = "10002"       # 这个号登录的是谁
  ```

- **一个账号一条连接**。同一个平台上想挂两个号，就写两条连接（`qq`、`qq2`），不是一条连接
  带两个号。平台的硬事实：一条 WS 连接就是一次登录，就是某一个号。
- **房间的第一段是连接名**，不是平台名：`qq:group/123`、`qq2:group/123`。两个号看同一个群
  = 两个房间，各记各的流水和水位，永远不会互相踩。这是「同平台多条连接」能成立的前提。
- 出站按连接分发：发往 `qq2:group/123` 就交给 `qq2` 那条连接的适配器。没有名叫 `qq2` 的
  连接就明确报错，不静默丢。
- `kind` 说协议（`onebot11`），`transport` 说方向（`ws-client` / `ws-server`）。两件事分开
  写，以后加 HTTP、反向 WS 不用把名字拼长。
- `account` 必填：桥靠它认出「这句是我自己发的」。连上之后会跟平台报的号核对一次，对不上
  只警告（不影响收发，但自己的话会被当成别人说的）。
- 启动校验：连接名重复、`kind` / `transport` 不认识、`ws-server` 还没实现、地址不是 `ws://`、
  `account` 空——都在启动时报错，不带病运行。

## 不这样会怎样

拿平台当连接的身份（早先的做法），第二个号就没有位置：配第二条直接报错，或者两条连接互相
覆盖。更要紧的是房间键：如果房间是「平台 + 房间号」，两个号看同一个群会写进同一个房间——
一份流水、一份水位、两份重复投递。所以「同平台多条连接」这件事绕不开「房间第一段换成
连接名」，两件事必须一起改。

## 技术细节

- `Outbound::send(room, elements)`——设备、账号这些参数都去掉了。一条连接一个实例，它自己
  就知道自己是谁、从哪个号发。`Outbounds` 是 `HashMap<连接名, Box<dyn Outbound>>`，按
  `room.connection` 查表。
- 连接方式先只做**正向 WebSocket**（桥当客户端去连 OneBot 的 WS 服务端）。反向 WS 要桥自带
  WS 服务端，多一层监听与鉴权；真需要时加一个 `transport` 取值即可，配置形状不变。
- 每条连接一个守护线程：连不上每 5 秒重试，断了自动重连，进程不退出。
- 一个线程同时管读和写：读带 20ms 超时，超时只是「这会儿没消息」，回头把排队的动作写出去。
  这样不需要拆 socket，也不会出现「读阻塞导致回复发不出去」。
- 写动作走队列，由同一个线程按 `echo` 配对回包——写和读永远只有一个执行者，不会串字节。
- 往桥里喂事件用 `try_lock`：桥的锁可能正被回合线程拿着（它正在等平台回话）。抢不到就
  先攒着，绝不在等锁的时候卡住写动作，否则两个方向互相等死。
- 依赖 `tungstenite`（阻塞式 WebSocket，无异步运行时），与「单进程、每连接一线程」的
  并发模型一致。
