# ADR-0017 多 agent 模型：device 升级为「harness 会话」，记忆独立成可共享的 git 仓库

来源：用户裁定（2026-10-29 起多轮对话敲定；本文所有标「用户裁定」的句子都出自用户原话，
其余为实现默认，可推翻）。

## 这条决定了什么行为

桥从「多 harness × 多设备」升级为「多 harness × 多 harness 会话」，核心是把两件一直绑在一起的
事拆开：**「谁在说话、在哪活动、怎么串行」** 和 **「它记得什么」**。前者归会话，后者归记忆。

### 五个一等对象（用户裁定）

- **社交平台连接列表**：一条连接 = 一个平台账号，同平台可多条（沿用 ADR-0012）。
- **人格列表**：一个人格 = 一张纯文本人设卡（`id` + `name` + 「你是谁 / 什么性格 / 什么语气」
  的正文）。人格**不带记忆、不带订阅**，只是「怎么说话」的文本；投递给模型时注入系统提示词
  （对应旧 node 实现的 `roles/<名称>.md`，用户裁定）。
- **记忆列表**：一份记忆是一个**抽象接口**（`id` + `name` + `type` + 与 type 对应的位置/参数），
  底层存储形式由 `type` 决定、可扩展（用户裁定：记忆不该只有 git 一种形式）。**`type: git`
  只是第一种实现**（字段 `path` + 共享方式 `worktree`），未来可加 sqlite / 云数据库 / 向量库等。
  记忆是**长期知识**，独立存放、可被多个会话共享，最终一致（用户裁定）。
  - **桥不定义「什么是记忆」**（用户裁定）：桥只给 harness 三样东西——**仓库路径 + 文件能力 +
    git 能力**，「记忆」的语义由会话自己约定（综合文档叫啥、订阅怎么分目录、一条记忆是什么，
    都是会话自己的事）。桥不是「记忆语义层」，不封装「存一条 / 取一条」这种高层动作。
  - **harness 直接拿「文件 + git」两层能力**（用户裁定）：枚举的是「文件操作 + git 操作」这一整套，
    不是只枚举 git。文件层（读/写/列出 `*.md`）是「记忆内容」的本体，git 层（add/commit/diff/log/
    blame/push/branch）是「记忆的版本与同步」；没有文件读写，git 记忆仓库就是个读不进也写不出的空壳。
  - **git 仓库的写也完整放开给 harness**（用户裁定）：桥对 git 仓库**不做任何提交 / 推送 / 建分支 /
    改内容**等操作，唯一例外是「初始化 worktree」这类把仓库准备好的基建活。其余文件 + git 能力全部
    由 harness 直接持有，桥只负责把仓库初始化到位、并告诉 harness「当前会话的 worktree 路径」。
- **harness 列表**：一个 harness = 一个接管者（`id` + `name`）。桥**不主动连 harness**——是
  harness 反过来连桥、报出名字 + 令牌。所以桥对 harness 只存「有哪些、id 是什么」用来校验会话
  的引用，不存它的连接地址或内部配置（类比连接列表，但方向相反：连接是桥主动连平台，harness 是
  harness 主动连桥）。会话的 `harness` 字段引用这里的某个 id（用户裁定：harness 升为一等对象）。
- **harness 会话列表**：一个会话 = 一个串行单元，字段 `id` + `name`（可空，缺省 = id）+
  `harness id` + `人格 id` + `记忆 ids`（可空）+ `model`（可空）+ `订阅列表`。串行键 =
  **harness id + 会话 id**（用户裁定）。`model` 挂会话上（用户裁定）：每个会话可独立指定用哪个
  模型，空则由 harness 侧自己决定；桥侧只负责把它存好、随投递带给 harness，真正切换模型由各
  harness 自己实现（dsh 改 profile、opencode 改 config）。

### device 概念删除（用户裁定）

旧的「设备（device）」概念取消，升级为「harness 会话」：

- 一个会话 = 一个人格 + 一组订阅 + 可引用多个记忆。
- 一个 harness 进程连上来时，声明「接管哪些会话 id」——这是旧「一把令牌代表一组设备」的
  继承形态，但语义从「一组设备」改成「一组会话」。
- 会话串行键不再等于记忆：同一会话内部严格串行（类人），不同会话各自并发、互不排队。

### 记忆与运行态彻底分家（用户裁定）

- **记忆（长期知识）**：一个抽象接口，最终一致。会话引用多份，可空（空 = 不存长期记忆）。
  底层实现由 `type` 决定，当前第一种是 **git 仓库**（用户裁定「git + 日记」是最先想到靠谱的
  方式，但明确记忆不该只有 git 一种形式）：
  - git 实现下，仓库内按 `会话 id / 订阅 id /` 分目录，各会话写各自目录，天然不冲突（实现默认）；
  - 每份仓库再有一份「综合文档」跨会话承载共识，只有它才真正发生 git 冲突、需要 merge
    （实现默认）；
  - 多份记忆之间互不写，各是各的（实现默认）。
  - git 实现下 worktree 的职责：让每个会话 checkout 自己的工作目录，解决「多个会话同时写
    同一份记忆」的冲突、避免共享工作区互踩（实现默认）。
- **运行态（水位 / 未读 / 归档）**：**仍由桥管理、强一致**（用户裁定，纠正了此前「harness
  自己管」的口误）。但**按会话独立**——每个会话自己的水位、自己的未读、自己的归档，互不串。
  - 含义：桥的存储层里，运行态数据的归属键从「记忆名」改成「会话 id」；桥仍是唯一记水位、
    投未读、存归档的地方，投递正确性仍强一致，不因记忆最终一致而退化成可能丢消息。

### send_message_to 的边界（用户裁定）

`to` 的可发目标 = **当前会话订阅的所有房间**。**跨 harness 会话发送被砍掉**：一个会话不能
替别的人格/会话发言。因此旧「设备组订阅并集」的跨设备发送能力不再存在，`to` 收缩为本会话
订阅集。

## 不这样会怎样

- 如果继续让记忆既当「长期知识」又当「串行锁」（旧模型，ADR-0003）：只要两个会话共用一份
  记忆就自动排队，等于「跨 harness 共享记忆」这件事从根上没做成——共用即互斥，git 也派不上
  用场（排队的场景根本不会并发写）。
- 如果运行态也交给 harness 进程自己管（曾误选的方向）：投递正确性退化成最终一致，harness
  挂了会漏投 / 重投，会话迁移要带着水位走，桥查不到完整归档。这是会丢消息的，不可接受。
- 如果不砍跨会话发送：一个会话能替别的人格发言，权限边界形同虚设，且与「一个会话一个
  串行单元」的模型自相矛盾。

## 技术细节

- 串行键从「记忆名」改成「harness 名 + 会话 id」。影响 `crates/kernel/src/engine.rs` 的
  `active` / `by_ticket` 两处（现在都按 memory 串行），以及 `config.rs` 里「共用记忆排队」
  的警告逻辑（那个警告随着 device 删除一并消失）。
- 会话接管声明：harness 连接时携带会话 id 列表，桥据此建立「harness ↔ 会话」映射；一个会话
  同一时刻只能由一个 harness 代表，一个 harness 可代表多个会话。
- 人格注入：投递时把会话绑定的那张人设卡文本注入系统提示词，热生效（可改卡不重启）。
- 记忆接口抽象：桥与 harness 面对一个「记忆接口」，不关心底层 `type` 是 git 还是别的；加一种存储
  形式只动实现层，不改桥与 harness 的用法。**桥不定义「什么是记忆」**，只提供「仓库路径 + 文件
  能力 + git 能力」三样，记忆语义由会话自己约定（用户裁定）。对 git 这种实现，枚举的是「文件操作 +
  git 操作」一整套（文件读/写/列出 + add/commit/diff/log/blame/push/branch），**读写自然分列**，
  不需要再单独设一道「读/写」抽象去拆；「能不能写」由会话/适配器配置单独决定。桥对 git 仓库唯一
  保留的动作是「初始化 worktree」这类基建，绝不做提交 / 推送 / 建分支 / 改内容（用户裁定）。
- git 实现的记忆仓库布局（实现默认，可推翻）：
  ```
  <memory-repo>/
    <session-id>/<subscription-id>/*.md   # 会话各自写，天然不冲突
    shared.md                             # 综合文档，跨会话共识，才需要 git merge
  ```
- 运行态表结构：`watermarks` / 归档记录 的主键从「记忆」改为「会话 id」，桥内锁按会话串行。

### 旧预设的「无本地工具」与新架构冲突（用户裁定：选 a）

旧 node 实现的 qq-chat-v2 预设里，有一句**安全规则**「你没有本地工具：不能执行命令、不能读写
文件、不能启动程序」（`dsh/agent-presets/qq-chat-v2/agent.cordis.yml` 的 persona.prefix 第 1 条），
再配合 `qq-tool-restrict` 插件在**执行期白名单**兜底拒绝越权工具。这**不是 harness 或 MCP 的能力
缺失**——bash/git 这些能力在 harness 层一直都在，只是旧产品定位「混在 QQ 群闲聊的仿真人格」主动
用规则把它封死了：既不让模型产生「我能碰本地」的念头，又在工具层物理兜底。

新架构要让 harness **直接操作 git 记忆仓库**，与这条规则正面冲突：照搬旧预设，git 能力等于白给。
这不是「恢复一个被阉割的能力」，而是**人格/预设的安全边界要重定**——会话从「不许碰宿主机的聊天
仿真」变成「有自己 git 记忆仓库、本来就该能碰 git 的 agent」。

**结论（用户裁定，选 a）**：把「安全规则」和「能力」彻底分离，并删掉「你没有本地工具」这条——
- **人设卡只管内信息边界**：什么不能说、什么不能漏（凭据 / 本地路径 / 私聊内容 / 内部配置）。
  人设卡不再声明「你能不能用 bash / git / 工具」。
- **能力全交给配置层**：能不能用工具、用哪些，由 **harness 侧配置 / 适配器**单独决定；能不能 bash /
  git、git 能不能写，由**会话配置**单独决定。要 git 的会话就把 git 能力打开，反之不开。
- 三层各管各的：人设卡 = 「是谁 + 什么不能漏」；会话配置 = 「给这个 agent 多少能力」；harness/适配器 =
  「这个运行环境实际挂出什么工具」。三者不混，换 harness 或换适配器不需要改人设卡。

## 被取代 / 需要修订的旧 ADR

- **ADR-0002（订阅模型）**：「设备」→「harness 会话」；「一把令牌代表一组设备」→「一个
  harness 声明接管一组会话」。订阅仍挂「连接 + 房间 + 三条策略」，这部分不变。
- **ADR-0003（串行轮次）**：「串行键 = 记忆名」→「串行键 = harness 名 + 会话 id」；「共用记忆
  自动排队」删除。一轮只投触发房间未读、水位/流水按房间记，这部分不变。
- **ADR-0010（ack 水位）**：水位推进逻辑不变，但归属键从记忆改成会话，需随引擎一起改。

## 待定 / 后续

- 「综合文档」的 merge 冲突策略（谁先到谁赢？还是交给模型合并？）未定，先落地目录分层的
  无冲突路径，综合文档先只读、后补写。
- 会话的持久化位置（是否与会话 id 一起存在桥库、还是散在各自 harness）未定，实现时定。
- **记忆的其它存储形式**（sqlite / 云数据库 / 向量库等）只定义了「type 可扩展 + 接口不变」的
  原则，具体 `type` 值和接口签名实现时再细化（用户裁定：记忆不该只有 git 一种形式）。git 这一种的
  接口形态已定：**文件 + git 两层直接交给 harness、读写自然分列、桥只管路径与 worktree**；其它
  `type` 是否也沿用「把底层能力透出去」的思路，实现到那一步再定。

## 实现记录（2026-10-30）

- 会话模型改造（device → 四对象）已落地：config 拆 Persona/Memory/Session，串行键改
  「harness 名 + 会话 id」，`send_message_to` 收缩为本会话订阅集，协议 v2→v3（hello 加
  harness、delivery 的 device/memory 合并成 session），水位键 device→session，schema 3→4。
- 记忆接口（git 实现）已落地：
  - `Memory.location` = 裸 git 仓库路径，桥用 git2 库 `init --bare` 就位（空仓库）。
  - 配置加 `worktrees_root`（默认 `state/worktrees`），每个「会话 × 记忆」的 worktree 路径
    固定为 `根/记忆id/会话id`。
  - 惰性初始化 + 幂等：worktree 存在且有效就复用，异常就报错，不存在才 checkout；空裸仓库
    （HEAD unborn）直接 `init` 成独立仓库（无历史可共享）。
  - 文件 + git 工具加进桥的工具清单（`memory_read/write/list/search` + `memory_git_*`），
    走现有 `tool_call` 帧、带 ticket；每个工具带 `memory` 参数指认操作哪个仓库；所有路径
    锁死在 worktree 内，`..`/绝对路径越界一律拒绝。
  - `Delivery` 加 `memories` 字段（id + worktree 路径），投递时带给 harness。
  - git 的写（add/commit/push/branch）完整放开给 harness，桥只做「第一次建 worktree」；
    commit 无 user.name/user.email 时用桥固定身份兜底。
- harness 升一等对象 + 会话加 name/model（用户裁定，2026-10-30）：
  - `Config` 加 `harnesses` 列表（`Harness { id, name }`），`Session.harness` 从「自由字符串」
    改成「必须引用一个已声明的 harness id」（校验 `UnknownHarness` / `DuplicateHarness` /
    `EmptyHarnessField`）。
  - `Session` 加 `name`（可空，缺省 = id）与 `model`（可空）。
  - `Delivery` 加 `session_info`（`SessionInfo { id, name, harness, model }`，可选、向后兼容），
    投递时桥填好带出去，harness 据此知道「以什么身份说话、用哪个模型」。
  - model 只挂会话、桥只透传：dsh 的 `session/prompt` 与 opencode 的 `ctx.session.prompt` 都
    不接 model 参数，模型实际由各 harness 自己的 profile/config 决定；harness 侧先消费
    `session_info.model` 做日志透传，真正的模型切换留待各 harness 自己实现。
