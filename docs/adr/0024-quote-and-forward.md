# ADR-0024 引用对齐、转发展开、目录给样例

来源：用户裁定（「做个反馈接口，另外举一反三，很多问题不仅是这里有，那里也有」，以及「绕道如果涉及安全问题，那是后续 dsh preset 侧的事」2026-10-31）；具体做法（桥做还是适配器做、字段名、上限）属实现默认。

## 三件事，一个病

这三条是同一个病的三种表现：**桥手里有对齐所需的信息，却让 agent 自己去拼**。

| 症状 | 桥手上有什么 | 缺的那一步 |
|---|---|---|
| 引用对不上（`[引用 #-1179324851]`） | 平台编号 ↔ 本房间编号的对应关系（就在流水里） | 投递前查一次 |
| 合并转发要一层层点 | 能自己去问平台的通道（`get_forward_msg`） | 适配器递归取 |
| 目录不可机读 | 参数表（每条的 `ParamSpec`） | 照参数表填一个样例 |

三条都属于「把该做的事做完」，不是给工具加功能。所以不新增工具位：`get_history` 多一列、`message.forward_content` 多两个参数、`platform_methods` 的详情档多一个字段。

## 引用对齐：`quote_ref`，两个号并排

平台在引用段里只给**它自己的**消息编号（QQ 是 `-1179324851` 这种），而 agent 在对话里看到的是本房间的水位编号（`#621`）。两者之间差一次反查。

桥在投递和查询时补上，形状是：

```json
{"quote_ref": {"platform_id": "-1179324851", "id": 621}}
```

- **两个号都给**，不是一个换成另一个：平台编号在调平台方法（撤回、取原消息、回复）时要用，水位编号在本房间翻历史、确认未读时要用。
- **查不到就给 `{"platform_id": "..."}`，没有 `id`**。不要给 `id: 0` ——「0」会被当成一条真记录。查不到本身是信息：可能被清理了，也可能引用的是别的房间/别的平台的消息。
- **不落盘**。`quote_ref` 是算出来的：被引用那条可能后到（乱序投递），可能早被清理；存下来只会存出一个假的对应关系。落盘的仍然只有 `platform_id`（事实）和水位编号（编号本身就是事实）。
- 渲染在 harness 侧：`[引用 #621]`。查不到时写 `[引用 #gone，本房间历史里没有这条]`——比给一个对不上的号强。
- 存储层为此加了 `Transcript::located(room, platform_id)`，并给 `records(connection, room_key, platform_id)` 建了索引（老库打开时自动补，不改结构版本）。
- `get_history` / `fetch_records` 的 `columns` 里多了 `quote_ref` 一列，**不进默认列**：不引用别人的消息占多数，默认带上就是白占预算；`columns` 状态表里那一项是 `false`，agent 看得见它存在。

## 转发展开：适配器递归，摊平成表

合并转发在 QQ 里是一条消息里嵌一个转发 id，展开一层又是同样的东西。以前 agent 要三跳：`message.forward_content(id)` → 看见内层 id → 再调一次 → 再调一次。

**这是适配器的活**，理由和 ADR-0020「core 不认识任何方法名」是同一条：`get_forward_msg` 一次只给一层是 QQ 的规矩，不是桥的规矩，不该让 agent 替适配器跑循环。

做法：`message.forward_content` 增加两个参数（`depth` 默认 3、最多 5；`max_nodes` 默认 200、最多 500），适配器递归取、摊平：

```json
{
  "id": "root", "depth": 3, "returned": 12, "has_more": false,
  "nodes": [
    {"path": "1", "depth": 0, "sender": {"id": "10002", "name": "小李"},
     "at": 1700000000000, "text": "[合并转发]", "forward_id": "inner", "content": [...]},
    {"path": "1.0", "depth": 1, "sender": {"id": "10003", "name": "小张"},
     "text": "对的对的", "content": [...]}
  ],
  "leaf_text": "转给你\n[合并转发]\n对的对的"
}
```

- `path` 是位置（`1.0` = 第 2 条的第 1 个回复），`depth` 是层数；光有缩进没有路径，模型引用的时候还是说不清是哪条。
- `leaf_text` 是全部节点正文拼起来的一段话——嵌套再深，读这一段就知道最里面说了什么，不用逐层翻。
- 每个节点带原始 `content` 段，要转发回去照抄即可；桥不重写内容，只加位置。
- **三个上限都是硬的**：层数、节点数、以及「同一个转发 id 只展开一次」（防平台数据自引用）。
- 到上限时 `has_more: true`，并且节点里留着 `forward_id`——想继续看就把那个 id 再喂进来，不用从头展开。

## 目录给样例：`example`

`platform_methods` 的详情档（给了 `group` / `tag` / `query`）本来就有 JSON Schema。加一个 `example`：

```json
{"method": "message.send_group", "params": {"group_id": "123456", "message": [{"type": "text", "text": "你好"}]}}
```

- **照必填参数生成**，可选参数不塞进去（样例要短才有人抄）。
- 值是「像真的」的假值：群号 `123456`、QQ 号 `10000`、文件 `https://example.com/a.png`，不是 `<string>` 这种还得翻译一遍的占位符。
- 只进详情档。清单档（不给条件）五十来条都带样例，清单就没法看了。
- 样例是**生成**的，不是每条手写的：手写五十二条的下场是表和实现对不上，而生成永远跟参数表一致。

## 不做的两件事，以及为什么

- **不做 `since`（方法从哪个版本开始有）**。我们没有任何可信来源能填这个值——填了就是编。真要知道「这个方法能不能用」，答案是看目录：目录里没有就是没有。
- **不做 `raw.passthrough` 审计出口**。绕过订阅表去连平台端口是能力缺口逼出来的，补缺口（这个 ADR 和 ADR-0022/0023）比堵路有用；而「拦住 agent 的 bash」根本不属于桥的层级——那是 harness（dsh preset / opencode 插件）该管的执行边界。用户裁定：这块放到 dsh preset 侧做，opencode 侧还没调查。
