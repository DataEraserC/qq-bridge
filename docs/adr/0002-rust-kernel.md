# 内核用 Rust

内核用 Rust 编写。

## 理由

内核是常驻进程，持有全部长连接与归档，对内存占用和长时间运行的稳定性有要求。Rust 同时给出一份无运行时依赖的单二进制，便于分发。

## 适配器的语言不由本决策规定

适配器的语言**跟着它对接的运行时走**，架构不约束。

适配器只依赖运行时的公开接口，不依赖内核的任何内部模型。所以它用什么语言，取决于那个运行时提供了什么。给 DSH 写的适配器用 TypeScript，因为 DSH 的 SDK 与工具协议实现在 JavaScript/TypeScript 生态里——这是「这个适配器」的选择，不是「适配器」这条规则。

换一个运行时，就按那个运行时的生态选语言。内核不受影响，协议不受影响：协议是 JSON 行，任何语言都能说。

这条区分是刻意的。把适配器的语言写死，等于给「适配器可替换」加一条架构本身不支持的约束——将来对接一个 Go 或 Python 生态的运行时，会被迫先自己写一层协议实现。

## 考虑过的方案

**两侧都用 Rust。** 只对「给 Rust 生态运行时写的适配器」成立，不能作为通则。

**内核用 TypeScript。** 内核会失去单二进制分发与内存控制，且长连接与归档的稳定性不如 Rust。

## 后果

- 构建链按适配器而定：内核固定 Cargo；DSH 适配器是 Node 包管理，别的适配器不一定是。
- 协议成为跨语言接口，字段演进需要两侧同步。这也是协议里「未知字段忽略、主版本不同即拒绝」这两条规则存在的原因。
- 「适配器用 TypeScript」不是架构事实，只是当前唯一实现的选择。文档描述具体适配器时说明语言，描述适配器这一层时不说明。
