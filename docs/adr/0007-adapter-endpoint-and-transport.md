# 适配器接入点与传输

内核与适配器之间的通道不是「一条 Unix socket」，而是**一个由配置决定的接入点**。这个决定要支持三件事：跨操作系统、跨机器、以及不因为换平台而改协议。

## 决定

`adapter.socket` 接受三种写法，帧格式完全相同：

| 形态 | 写法 | 实现 | 跨机器 |
| --- | --- | --- | --- |
| 文件路径 | `/run/user/1000/qqab.sock`、`\\.\pipe\qqab` | `interprocess` 的 `GenericFilePath` | 否 |
| 命名空间 | `local:qqab`（裸名等价） | `interprocess` 的 `GenericNamespaced` | 否 |
| TCP | `tcp://0.0.0.0:7000` | `std::net::TcpListener` | 是 |

## 理由

**跨平台不是将来才要的。** 适配器的语言随运行时（见 [ADR-0002](0002-rust-kernel.md)），运行时不一定是 Unix。若协议只跑 Unix 域套接字，那么「换个运行时」这条卖点会在 Windows 上直接落空——不是适配器难写，是根本连不上。

`interprocess` 把 Unix 域套接字与 Windows 命名管道统一到一套 `Listener` / `Stream` API，且它**不做任何自己的消息分帧**：写进去的字节原样从对端出来。协议已经有换行分隔的帧格式，所以这一层只提供传输，不侵入协议。

**跨机器只有 TCP 一条路。** 本机套接字的前提是共享文件系统或命名空间，那在另一台机器上不成立。三个理由（推送、低延迟双向、单机零端口）里，「零端口」是唯一会被跨机需求否掉的一条，而它恰好是最弱的一条。

**平台判断放在配置文本里，不放在编译期。** 判据是「有没有路径分隔符」，不是 `cfg!(windows)`。理由是配置可能由另一台机器上的部署者写、也可能由安装脚本生成；内核按自己所在的平台去重新解释一段已经写好的文本，会让同一份配置在两台机器上有两种含义。

## 考虑过的方案

**只做 TCP。** 最简单，跨平台跨机器都成立。代价是所有本机部署都要占一个端口并处理令牌，而绝大多数部署是单机的。丢掉了「本机天然隔离」这个默认安全状态。

**自己按平台写两套实现。** 大约两百行：`UnixListener` 一套，`CreateNamedPipe` 一套（还要处理 `PIPE_ACCESS_DUPLEX`、重叠 IO、实例数）。命名管道的正确用法比看起来复杂得多，而这不是本项目的核心复杂度。

**用 tokio 的 `UnixListener` + `named_pipe`。** 依赖 async runtime，与 [ADR-0006](0006-blocking-websocket-per-thread.md) 冲突。

## 后果

- **跨机器必须配令牌**，配置校验在启动期拒绝「TCP 监听非回环地址但没有 `adapter.token`」的组合。本机形态不强制：文件权限与命名空间隔离已经是边界。
- 令牌核对在 `hello` 帧里做（同一帧带版本），不是额外的握手步骤。比较用常量时间，长度不同也不提前返回。
- **Windows 命名管道不支持 IO 超时**（`interprocess` 的 `set_recv_timeout` 在那里返回 `Unsupported`），所以连接循环用**非阻塞 + 轮询**而不是「阻塞读 + 读超时」。两个平台上语义相同，于是只有一套代码。代价是空闲连接每 20 ms 醒一次——接入连接数是适配器数，不是消息数，这个代价可以忽略。
- 写也是非阻塞的：对端不读时不能把内核卡死。待发字节攒在缓冲里逐轮推，攒过 8 MiB 就断开那条连接。
- 缺省值仍是 Unix 路径 `/run/user/1000/qqab.sock`。Windows 部署必须显式写 `\\.\pipe\qqab` 或 `local:qqab`——没有做「按平台换缺省值」，因为猜测比写清楚更容易出错，而且猜错时的表现是「启动失败」而不是「连到错误的地方」。
