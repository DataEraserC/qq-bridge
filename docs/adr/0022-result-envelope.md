# ADR-0022 工具结果的统一信封：总数、分页、落盘

来源：实现默认，可推翻。起因是 agent 的实测反馈：「`get_group_member_list` 在 24 人的群里只回来 16 个，没有 total、没有 has_more，我只能猜」「15 个管理员到底是不是完整数字？」

## 旧做法错在哪

`platform_call` 的结果超过 8000 字符就变成：

```json
{"truncated": true, "total_chars": 24310,
 "preview": "[{\"user_id\":123,\"nickname\":\"老…"}
```

三个问题，一个比一个严重：

1. **`preview` 是字符串，不是结构。** 模型拿到的是一段半截 JSON 的字符串，它既不能当数组遍历，也不能按字段引用。「截断」变成了「报废」。
2. **只有字符数，没有条数。** `total_chars: 24310` 回答不了「一共几个人」——而这正是它唯一想知道的事。
3. **上限是死数，调大不解决问题。** 24 人的群截到 16 个，说明 8000 字符只够十来条；真碰上 1000 人的群，调成 80000 也只够两百条。

## 现在的规矩：一个出口，三条路

所有工具结果都从 `tool_call` 的同一个出口走（`kernel::render::fit`），而不是各工具自己截。这样新加的工具天然受保护——以前每个接口各自截断，于是截断方式各不相同，最糟的就是上面那种。

1. **装得下**（≤ 24 KiB）→ 原样返回，一个字节都不动，不加任何信封。
2. **主体是一个数组** → 按条分页：`total`、`offset`、`returned`、`has_more`、`next_offset`。返回的仍是同样的结构，只是数组短了、多了个 `_page`。
3. **还是装不下**（单条就巨大，或根本没有数组）→ 落盘到 `state/spill/`，返回 `path` + `bytes` + 开头 2 KiB 的 `head`。

24 KiB 是这么定的：约 6～8k token，一条工具结果占到这么多已经很重了；同时五十来个方法的目录、几十人的成员列表都要装得下——这些是正常操作，不该逼模型分页。按**字节**不按条数，因为要挡的是「撑爆上下文」，条数管不了这件事。

## 分页放在桥这一层，不放在平台方法里

`platform_call` 加 `limit`（默认 100，上限 500）和 `offset`。平台照旧一次给全，桥切片后再交出去。理由很实际：**五十个方法签名不动**。分页是「怎么给模型」的问题，不是「怎么问平台」的问题，混在方法签名里会让每个适配器作者都得想一遍这件事。

`slice` 认「最长数组就是主体」：平台结果形状千奇百怪（`data` / `list` / `members` / 直接一个数组），与其为每个平台写一条规则，不如认最长那个。分错了也只是分错东西，不会丢数据——`_page.total` 永远是真的总数。越界返回空页 + `total`，不报错：模型据此知道「翻到底了」，而不是「这个接口坏了」。

## 每个列表接口自己也要给总数

`render::fit` 是兜底（保护上下文），但它替代不了「你知道自己在给什么」。所以凡是会长的列表，自己带上总数与续页：

| 工具 | 信封字段 |
|---|---|
| `get_history` | `total` / `returned` / `has_more` / `next_before`（往更早翻传 `before`） |
| `fetch_records` | `total` / `returned` / `missing` |
| `get_platform_events` | `total` / `offset` / `returned` / `has_more` / `next_offset` |
| `get_notes` / `list_rooms` | `total` |
| `platform_methods` | `total` / `returned` / `matched` |
| `memory_list` / `memory_search` | `total` / `offset` / `returned` / `has_more` / `next_offset` |
| `platform_call` | `_page`（见上） |

`get_history` 用 `before` 而不是 `offset`：流水的编号只增不改，用编号翻页不会因为「中途来了新消息」而错位——新消息都在另一头。

## 落盘：谁读、多大、留几个

- 位置：状态库旁边的 `state/spill/`（跟库一起备份、一起清）。
- 名字：`<工具名>-<毫秒>.json`，同毫秒多次落盘加序号，不互相覆盖。
- 单个上限 4 MiB（超出只写前 4 MiB 并注明截断）；目录最多留 50 个，新的留着旧的删。
- **至少给 2 KiB `head`**：不是所有人都能读文件——harness 侧一般有读写，但不是每个都有。给一段开头，模型至少能判断「要不要去读全文」。
- 写盘失败也如实回报（`spilled: false`），不假装成功，也不把整个结果塞回去撑爆上下文。

## 顺带修掉的两处同类问题

同一个病（「悄悄截断，还不说清」）在别处也有，一起按这个 ADR 的原则处理：

- **`get_platform_events` / `memory_search` 以前无声截断**（后者干脆不截，命中上万行时会直接撞上 1 MiB 的帧上限，harness 解帧失败、断连，看起来像「桥挂了」）。现在都带 `total` + 分页。
- **投递帧也可能超限**：`delivery_limit` 是按条数截的，200 条长消息照样能撑过 1 MiB。现在 `open_turn` 追加一道 512 KiB 的字节预算，并按「最旧一小段 + 最新一批」选批；跳过的中段用 `omitted {from, to, count}` 明确给编号区间，`more` 等于 `count`。

## 不这样会怎样

- 保留 `preview` 字符串：模型继续在半截 JSON 上瞎猜，而且这次连「一共几条」都没有。
- 只调大上限：24 人 → 1000 人时同样的事再发生一次，只是更难发现。
- 让每个工具自己截：新工具接着犯同样的错，而且风格各不相同——这正是这次要一次收口的原因。
