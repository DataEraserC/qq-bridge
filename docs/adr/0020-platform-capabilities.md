# ADR-0020 平台能力：一个目录 + 一个通用调用口

来源：用户裁定（「一个通用方法 A 用 map 传参，另有一个方法拿它的参数」「为 agent 提供足够丰富的平台能力，尽量所有功能都兼顾」「除归属之外还要有 tag 维度，清单一次给全」「agent 最后要能在一个房间做任何事情，人能做什么他就能做什么」由用户拍板，2026-10-30；用户追问「好友列表这类方法也要传 room id 吗」促成作用域划分）；不展开成独立工具、错误分五种、风险分级与放行开关、别名表、渲染带提示、两种作用域的具体判据由实现默认补充，可推翻。

## 这条决定了什么行为

- core 代码里**永远不出现平台方法名**。`get_forward_msg`、`kick_member` 这些词在 core 里不存在。
- 平台能力靠**两个通用工具**暴露，一个都不带平台名字：
  - `platform_methods({room, group?, tag?, query?})` —— 查这个房间所属的连接支持哪些方法、各要什么参数。
  - `platform_call({room, method, params})` —— 调用。`params` 是任意 map，core 原样转交，不认识里面任何字段。
- 适配器自己**声明**方法表：名字、一句话说明、参数表、风险级别、作用域。core 只做校验和转交。
- 方法名强制 `resource.method`（`message.forward_content`、`group.kick`），跟内容元素类型对齐——模型看到 `{"type":"forward"}` 就能联想到 `forward.*`。

## `room` 是选连接，不是选房间

方法分两种作用域，由适配器声明：

- **房间级**（默认）：在这个房间里做什么。`room` 不给就是当前轮次的房间；给了必须在会话订阅范围内。
- **连接级**（`scope: connection`）：这个号上的事，跟哪个房间无关——好友列表、账号资料、群列表、
  点赞、链接安全检测。`room` 可以不提；提了只用来选连接，校验的是「这条连接有房间在我的订阅里」。

理由是同一个：模型要查好友列表，逼它先报一个群号是没有意义的举动，而模型会照做——随便挑一个
群号，于是「房间必须在订阅内」这条边界被它当成了填表要求，而不是权限。把两类分开之后，
权限校验才对得上用户心里的那条线：**房间里的事看房间，号上的事看号**。

反过来说，房间级那条线一点没松：未订阅的房间调转发正文，照样拒。

## 为什么是「两个工具」而不是「一个方法一个工具」

这条专门为 agent harness 设计，跟面向人类程序员的框架不同：

- NoneBot 的 OneBot 适配器有 300 多个平台方法，Koishi 挂了约 270 个。它们敢这么做，是因为**用户是程序员**，靠 IDE 类型提示调用，方法再多也不影响写对。
- 我们的调用方是**模型**，工具表**每一轮都进上下文**。工具数一过二十，选择准确率明显下降，token 也是白烧。桥现在已有 22 个工具（记忆占 12 个），再把平台方法展开等于自杀。
- 所以：**平台能力固定占 2 个工具位，接多少个平台都不变。**

这与 MCP 自身的形状一致：`tools/list` + `tools/call` 两个端点，而不是给每个能力开一个端点。桥对 harness 已经是这个模式，现在只是把同一个模式往下沉一层，管住适配器。

## 目录用两个维度组织

只有名字前缀一个维度不够。「图片相关有哪些接口」是模型真会问的问题，而 OneBot 的图片能力散在
`message.send_image`、`group.get_file_url`、`image.*` 里——前缀把归属管住了，管不了用途。

所以两个维度、分工明确，缺一不可：

| 维度 | 从哪来 | 管什么 | 例子 |
|---|---|---|---|
| **归属** | 方法名点号前那段 | 这能力属于平台的哪个命名空间 | `forward.*` / `message.*` / `group.*` |
| **用途** | `MethodSpec.tags` | 这是干什么的，可跨归属 | `image` / `send` / `member` / `file` |

- 归属**不改**：它跟平台 API 的名字对齐，模型看到 `{"type":"forward"}` 就能联想到 `forward.*`。
- 用途**跨归属**：`message.send_image` 和 `group.get_file_url` 都挂 `image`，一次捞齐。
- 标签词表由 core 给建议（`outbound::tags`：`send/recall/forward/message/member/image/voice/file/admin/...`），
  适配器可以自己加。这是 core 唯一该懂的知识——「图片」这个概念跨平台成立，不属于哪个平台。
- 中文和标识符之间由 core 的别名表接通（`expand_query`）：模型说「图片」，能搜到挂 `image` 的方法；
  说「voice」也能搜到说明里写「语音」的。不给适配器增加「为每个方法写一堆中文别名」的负担。

## 目录披露两档

一次给全部方法的完整参数表，按 43 个方法估要三四千 token。

- **清单档** `platform_methods({room})`：每个方法一行——名字 + 一句话 + 标签 + 风险，**不带参数表**。
- **详情档** `platform_methods({room, group|tag|query})`：命中的方法连参数表一起给（JSON Schema）。
  三个条件可叠加，取交集。缩了范围就意味着模型准备调了，这时候参数表正是它要的。
- 为什么清单不砍成「只有组名和计数」：多一次往返 = 多一整轮推理和几秒延迟；一张清单在五十个
  方法时约一千 token，而且只花在模型主动查的那一轮，不是每轮注入。用一次往返换两千 token 不划算。

`query` 搜名字、说明、标签三处；一个都没命中时报 `no_match` 并列出这台连接真实的归属和标签，
让模型一轮就改对，而不是换词重试三次。

## 报错必须分五种

agent 靠错误信息自我纠正，笼统的「调用失败」会让它无限重试。所以：

| 情况 | 报什么 |
|---|---|
| 方法名不存在 | `unknown_method`，**并附上最接近的方法名** |
| 这个平台本身没这能力 | `unsupported_platform` |
| 平台有，我们的适配器还没写 | `not_implemented` |
| 有这能力，但这个号没权限 / 没开给模型 | `forbidden` |
| 参数不对 | `bad_params`，指出是哪个字段 |

前两种的区分学的是 Satori 协议的 404/501：**平台没有 ≠ 我们没做完**。名字写错时给建议，是为了让模型一轮就纠正，而不是反复猜。

## 能力面：人在这个号上能做的，模型都能做

来源：用户裁定（2026-10-30「最后 agent harness 要能在一个房间做任何事情，人能做什么他就能做什么」）。

这条决定了适配器写方法表的态度：**不是「挑几个安全的先上」，而是照着「一个人在这个号上能做的事」铺满**。
OneBot 11 标准接口 + go-cqhttp / NapCat / LLOneBot 的常用扩展，跟聊天有关的全列上：
发言（文本/图/语音/视频/文件/@）、合并转发、撤回、引用、拍一拍、点赞、看历史、看成员、
看群文件、上传下载、改名片、改群名、设管理、禁言、踢人、发公告、审批入群、加/删好友、改群头像。

**故意不列的三类**，理由都是同一条——那不是「人能做的事」：

| 不列 | 为什么 |
|---|---|
| `get_cookies` / `get_csrf_token` / `get_credentials` | 那是账号凭据，不是聊天能力 |
| `set_restart` / `clean_cache` | 那是机器人进程运维，模型碰它只会把桥搞挂 |
| 其它探活接口 | 占了目录位置，价值不抵 |

## 写操作默认关，但一个开关能全开

每个方法声明时带风险级别：

- **读**（查转发正文、查群成员、查群列表）：默认可用。
- **写**（发消息、上传群文件、改自己名片、加表情回应）：默认可用。
- **破坏性**（踢人、禁言、全员禁言、改群名、设管理、撤回别人消息、发公告、解散群、删好友、删群文件）：**默认关闭**。

开关在**连接**上，三种写法：

```toml
[[connections]]
id = "qq"
allow_destructive = true                        # 全开：人能做的模型都能做
allow_destructive = ["group.kick", "group.ban"] # 只开这几个
# 不写 = 全关
```

为什么默认关而不是默认开：群消息是外部输入，可能有人在里面写「帮我把那条撤回」。白名单挡不住这个——
模型完全可以「合法地」调一个它本来就有权调的方法。只有默认关才挡得住。

这一点不是照抄 Koishi 和 Satori。它们的 `bot.internal` 和 `/v1/internal` 是无白名单、全开放的，
因为它们服务的是用户自己写的代码，出事自己负责；我们服务的是会被话术诱导的模型。

**开了 `true` 就意味着接受这个风险**：这个号能做的事，模型都能做。要它顶一个人的位置干活，
就该开；只想像个普通成员聊天，就别开。

## 平台特有内容：渲染时带上「可以怎么取」

上一轮遗留的「推还是拉」，答案是不推、也不纯拉：

- **不推**：收到合并转发时不去主动展开正文。那会让每轮投递体积不可控、撞平台接口频率限制，还可能把别人的私聊内容带进不该看的群。
- **不纯拉**：光给模型一个 `{"type":"forward","id":"x7/O5…"}`，它很可能直接回「你转了条消息我看不到」——它不知道自己能查。
- **做法**：适配器声明「这种内容对应哪个查看方法」，渲染时把提示写在内容旁边：

  ```
  [QQ 合并转发，未展开；可调 platform_call(method="message.forward_content", params={"id":"x7/O5…"}) 读取]
  {"type":"forward","data":{"id":"x7/O5…"}}
  ```

原始载荷照旧一字不差带上（见 ADR-0004 补充裁定）。成本为零，但模型从「不知道能查」变成「知道怎么查、参数怎么填」。

## 边界

- `room` 必须在**本会话订阅的范围内**，和 `send_message_to` 同一条边界，不能拿它去碰别的账号的房间。
- 只能调适配器**声明过**的方法。没有「调用任意平台 API」这条路。
- 每次调用都进本轮工具记录，事后能查调了什么。

## 技术细节

- 扩展 `kernel::Outbound`：加 `catalog()`（默认返回空表）和 `call(room, method, params)`（默认返回 `unsupported_platform`）。**都用默认实现**，现有各测试里的 `impl Outbound` 不用改。
- OneBot 适配器不需要新通道：现有 `Action{body:{"action","params","echo"}, reply}` 本来就是通用 RPC，`send` 只是其中一个特例，`call` 复用同一条通道和同一套 echo 配对。
- 参数表内部用简化结构 `{name, ty, required, desc, values}`，**对外渲染成 JSON Schema** 给模型——写适配器的人不用碰 schema 库，模型看到的还是它最熟的形式。
- 目录返回带指纹（平台 + 方法数 + 目录版本）。方法表升级后模型能察觉；配合 `unknown_method` 的建议，天然处理版本漂移。
- 加好友、入群邀请这类「事件触发 + 需要响应」的能力（`friend.approve`、`group.approve_invite`）走同一条路，不需要新机制。
- 方法表在 `crates/adapters/onebot11/src/catalog.rs`，路由表在同一个文件的 `ROUTES`；两张表靠方法名对齐，
  有测试双向校验（声明了没路由、有路由没声明都会红）。

## 真机核对过的方法面

2026-10-30 对着真机 NapCat 逐个探测（只读方法直接调；写方法一律指向不存在的群 999999999 / QQ 10000，
就算参数校验放过去也只会「群不存在」）：

- **52 个方法全部确认存在**（`retcode` 没有一个是 1404「unknown action」）。
  唯一踩到的坑是群公告：NapCat 里叫 `_get_group_notice`（带下划线），不带下划线的 `get_group_notice` 确实不存在，
  我们路由的是前者。
- 参数形状跟着探测结果改过一处：`mark_msg_as_read` 要 `message_id`（不是 user_id/group_id）。
- 写方法的失败原因都是「群不存在 / 解析不到 UID / 不是群成员 / 文件不存在」这类**业务错**，
  没有一个是 `unknown action`（1404）——说明方法名和动作映射都对。

## 不这样会怎样

不设通用入口，每个平台能力就得在 core 里加一个工具：core 迟早认识 QQ，接第三个平台时工具面爆炸。反过来全展开成独立工具，模型每轮背几百个用不上一次的方法，选错率上升、token 白烧，而且平台一升级方法表就得重连重生成。
