# ADR-0018 桥侧统一控制台 + 会话映射落盘

来源：用户裁定（2026-10-30 对话敲定；本文标「用户裁定」的句子出自用户原话或明确选择，
其余为实现默认，可推翻）。

## 这条决定了什么行为

桥新增一个**统一控制台**：一个 HTTP 服务，用来在运行时**查看和控制**桥的运行状态，并延伸到
harness 内部——能管理「acb 会话 ↔ harness 内部会话」的映射、能重置某个会话。核心是把两条以前
一直缺失的能力补上：

1. **会话映射持久化 + 落盘到桥**：以前「acb 会话 → dsh 的 sessionId」这个映射存在 dsh 驱动的
   进程内存里，进程一重启就丢。现在改成**桥落盘**（类似上游 node qq-bridge 的 `sessions.json`），
   桥重启不丢、控制台能直接读。
2. **运行时控制面**：以前没有「改配置、重置会话、看状态」的入口，全靠改 TOML 重启。现在通过
   控制台 HTTP API 做，而且能**热生效**。

## 为什么选「桥侧」而不是「harness 侧」（用户裁定）

上游 node qq-bridge 是「桥自己直接驱动 dsh 会话、自己存映射」，所以它的控制台天然能管映射。
我们这次也**回到桥侧统一控制台**（用户裁定），不再把控制面板散在 harness 里。但有一个原则要
守住：**桥不越权定义 harness 内部的语义**——桥只做「指令的转发 + 状态的中转」，具体动作
（比如「重置 dsh 会话」到底怎么重置）由 harness 自己执行。这条跟现有「桥推 turn_start、
harness 自己决定怎么跑」的模式一致。

## 会话映射的形态

- 映射是一张表：**acb 会话 id → harness 内部会话 id**，再加元信息（标题、创建时间、模型、
  最后活跃时间等）。用户裁定要「带元信息」，控制台能展示更多。
- 落盘位置：桥的状态库（SQLite，`state/acb.db` 里新增一张表）。
- 桥对映射的理解止于「一个 kv + 元信息」：桥知道「这个 acb 会话在 harness 那边对应哪个 id」，
  但**不知道 harness 内部会话的细节**（那仍是 harness 自己的事）。

## 控制指令通道（协议 v4）

在桥 ↔ harness 的协议里加两条**控制帧**，让控制台能「触达」harness 内部：

- `Control`（桥 → harness）：`{ session, command, args }`。命令目前有 `reset`（重置会话映射）。
- `ControlResult`（harness → 桥）：`{ session, command, result }`。harness 执行完回报。

harness（驱动）收到 `Control` 后自己执行（比如 `reset` → 丢掉本地映射、下次开轮用新会话），
然后把结果回报给桥。桥不替 harness 做任何事，只负责转发和记录。

## 控制台 HTTP 服务

- 配置 `[console]`：`listen`（监听地址）+ `token`（鉴权）。
- **可远程访问**（用户裁定）：监听地址可配到非回环，配合用户远程控制（waypipe 等）的场景。
  因此鉴权必须认真做——远程 = 攻击面变大，token 校验不能省、不能弱。
- 端点（初版）：
  - `GET /api/sessions`：列所有会话 + 各自的映射状态（含元信息）。
  - `POST /api/session/:id/reset`：重置某会话的映射（桥发 `Control{reset}` 给对应 harness，
    等 `ControlResult` 回报）。
  - `GET /api/status`：桥的概览（连接、harness 在线情况、库统计）。
- 所有写操作都要 token 鉴权；读操作暂也鉴权（初版从简，一起鉴）。

## 与旧原则的关系（明确推翻点）

此前 ADR-0017 有一条「桥不定义什么是记忆 / 会话映射，harness 各管各的」。本 ADR 是**用户裁定的
演进**：会话映射的**存放**上移到桥（落盘、控制台可读），但**语义**仍留在 harness。桥存的是
「映射这个事实」，不是「harness 内部会话是什么」。边界不变：桥不碰 harness 内部怎么跑，只是
把「哪个 acb 会话 ↔ 哪个内部 id」这个事实记下来、能查能重置。

## 影响范围

- 协议升 v4（加两帧），桥和 harness 要同批次换。
- 桥侧：状态库加映射表、加 `[console]` 配置、加 HTTP 服务。
- harness 侧（dsh 驱动）：处理 `Control` 帧、回报映射、会话持久化（固定 sessionId + cwd 分组）。
- 控制台页面（HTML）作为后续工作，先落 HTTP API（API 稳定了页面才有意义）。
