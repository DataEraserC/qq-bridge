# 钩子宿主用 mlua vendored，资源上限靠 VM 指令钩子

钩子宿主落地时定了三件事：Lua 从哪来、沙箱靠什么封、死循环靠什么停。

## 决定

**Lua 用 `mlua` 的 `lua54` + `vendored`。** 源码随 crate 编译进二进制，不需要系统装 Lua，也不引入第二条运行时的构建链。ADR-0003 已定「内嵌 Lua 不引 WASM」，这里只是把「怎么内嵌」定下来。

**沙箱靠不给，不靠拦。** 建环境时只开 `COROUTINE`/`TABLE`/`STRING`/`UTF8`/`MATH`/`OS`，再把 `load`/`loadfile`/`dofile`/`require`/`collectgarbage` 置 `nil`，并从 `os` 里摘掉 `execute`/`remove`/`rename`/`exit`/`getenv`/`tmpname`/`setlocale`。不做指令级白名单、不做权限系统——威胁模型里脚本作者是部署者本人（ADR-0003），目标是防误用。

**资源上限用三步。** 单次调用有墙钟（默认 100ms）、VM 指令预算（每千条检查一次，默认两万条）、环境内存上限（4 MiB）。超限一律转成一次普通的 Lua 错误，由各挂载点的失败方向接住。

## 为什么不用 `table.freeze` 做只读配置

`table.freeze` 是 **Luau** 的扩展，Lua 5.4 没有。实测确认了这一点，所以只读快照改用代理表：`__index` 转发读、`__newindex` 抛错、`__pairs` 转发遍历，且**每一层嵌套都包一层代理**。

最后一处细节是这条决策真正的坑：只在顶层拦截时，`config.scopes[1].group = "9"` 改的是影子副本，看起来没报错、也确实没改到真配置，但脚本会以为自己改成功了。每层都代理之后，写嵌套当场抛错。

`rawset` 能绕过整个机制。这可以接受：防误改不是防恶意。

## 考虑过的方案

**不设指令预算，只设墙钟。** 墙钟靠指令钩子触发才能检查——没有指令钩子就只能靠另一个线程杀 VM，那需要 `Lua` 跨线程共享（`send` 特性，`Lua` 要 `Send`）。预算与截止时刻用两个原子量共享给指令钩子，是更小的实现，也让「超时」与「指令耗尽」走同一个错误路径。

**每条指令都触发钩子。** 精度更高，但每次 Lua 调用都要进一次 Rust 回调，正常脚本的耗时会被钩子本身主导。千条一次已是「两万条预算、二十次回调」的量级，足够。

**给每个环境独立线程与独立栈。** 宿主本来就在主循环里同步执行，钩子调用是微秒级。多一层线程只增加状态，不增加安全。

## 后果

- `mlua` 的 `vendored` 要 C 编译器。这是既有目标平台的既有限制（`rustls` 的 `ring` 也要 C 编译器），不是新增依赖。
- 内存上限统计的是 Lua 堆，不含宿主函数闭包持有的 Rust 内存。宿主函数持有的是几个 `Rc` 与设备名，不是脚本可控的量。
- 只读代理对 `ipairs` 直接可用，但 `pairs` 依赖 `__pairs`（Lua 5.4 认它）。这两条都写了测试，退化会当场失败。
- 脚本里的 `random()` 确定性来自设备 id 的散列。要真随机就得引入熵源，而排查「它为什么说话」时确定性更值钱。
