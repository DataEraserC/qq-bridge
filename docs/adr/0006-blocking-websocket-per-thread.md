# 连接用阻塞 WebSocket 与每连接一线程

OneBot 实现只提供 WebSocket。内核要同时持有 N 条长连接（每账号一条）和一份适配器接入服务端，决定用 `tungstenite` 的**阻塞** API，每条连接一个线程，不引入 async runtime。

## 理由

连接数是账号数，典型个位数以十计，不是以万计。每条连接的工作是「读一帧、交给管线、偶尔写一帧」——没有需要靠异步去摊薄的等待。`std::net` + `tungstenite` 的阻塞 API 直接给出这个形状，代码里没有 `async`/`await`、没有 executors、没有 `Send + 'static` 的传染。

更关键的是**测试形态**。内核的全部判定逻辑（归档、唤醒、队列、投递组装、事件解码、路由）现在都是纯函数，时间与随机数由调用方传入，没有一条测试需要网络或时钟。如果引入 async runtime，这些逻辑会先被 `async fn` 包一层才轮到被调用，测试就得先起一个 runtime——为了并发，付出的是整个内核的可测性。阻塞模型下，线程只在最外层：`transport` 读字节、呼叫纯逻辑、写字节。

## 考虑过的方案

**Tokio + `tokio-tungstenite`。** 生态标准，能省线程。代价是整棵树变成 async，队列与归档的接口要么全 async，要么在 async 与 sync 之间架一道 `spawn_blocking`。当前规模下省下的线程数没有意义，而可测性的损失是立刻的。

**`mio` 手写事件循环。** 线程更少、依赖更轻，但要把 WebSocket 帧的增量解析、握手、分片自己接一遍。`tungstenite` 已经把这些做对了，重写它没有收益。

**每个账号一个子进程。** 隔离更彻底，但归档必须跨进程共享，否则队列与水位对不上——那要引入一套进程间状态同步，比线程贵得多。

## 后果

- 连接数上限由线程数决定。几百个账号时会开始吃栈，届时换 tokio 是局部替换（只改 `transport`），管线与归档不受影响。
- `tungstenite` 的 TLS 特性**开启**（rustls + ring）：`ws://` 与 `wss://` 共用同一条读取循环，只是底层是 `MaybeTlsStream<TcpStream>`。选 ring 而不是 rustls 缺省的 aws-lc-rs，是因为后者要 cmake——交叉编译时多一层工具链依赖，而 ring 只要 C 编译器。
- 线程间共享的状态（连接池、管线）用一把 `Mutex` 串起来。争用点在事件处理与回合收尾，都是短临界区——不是热点路径。
