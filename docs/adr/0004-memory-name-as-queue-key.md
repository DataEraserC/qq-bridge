# 配置写记忆名，队列键也用记忆名

配置里的记忆用部署者起的名字标识，不用会话标识。串行队列的键同样用记忆名。

## 理由

会话由 agent 运行时创建，标识由运行时分配，且会话被回收后重建时会得到新标识。配置里写不出一个稳定的会话标识。

由此推出的第二条是：队列键也不能用会话标识。若按会话标识做键，会话重建的那一刻会出现两条并行队列（旧标识一条、新标识一条），把两条消息同时投进同一个新会话。记忆名在重建前后不变，所以它是唯一稳定的键。

## 考虑过的方案

**配置写会话标识。** 运行时分配，不可预知，会话回收后失效。不可行。

**配置写设备标识，队列按设备串行。** 两个设备共享记忆时会出现两条并行队列，投递进同一个会话。这正是要避免的情况。

**队列按群串行。** 一个设备订阅多个群时，不同群的回合会互相阻塞；两个设备共享记忆但订阅不同群时，又会出现并行。粒度不对。

**队列按 `(记忆名, 群)` 串行。** 一个记忆名第一次订阅第二个群时就会暴露问题：两个群本来就是两场对话，串行只是把 `(记忆名, 群)` 换成 `(记忆名)` 的退化写法。被拒的理由同上——同一个记忆名可以指向同一个会话，按范围拆键就会出现两条并行队列。

## 后果

- 适配器维护「记忆名与会话标识的映射，负责在会话重建时更新。内核完全不知道会话标识的存在。
- 「共享记忆」不需要额外机制：两个设备填同一个记忆名即可。这是唯一的共享方式，没有别的开关。
- 记忆名成为部署者可见的概念，需要写进用户手册。
- **一个记忆名可以订阅多个会话，它们共享同一份记忆，但排队。** 一个会话的回合进行中，另一个会话的消息只记积压；收尾时按「刚结束的会话优先、其余按名字」逐个投递，一次一个回合。这是刻意的：内核无从知道运行时能否同时吃两个回合（不同 harness 的能力不同），所以只能假设一个会话一次一个回合。
- **积压、唤醒原因与重投点都按 `(记忆名, 会话)` 记，不按记忆名。** 记成记忆名的会在收尾时只服务一个会话，把另一个的未读压到它下一条新消息才被看见——消息没丢，但不是「能正常处理」。
