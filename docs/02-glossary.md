# 术语表

> 状态：草稿，等用户过目。目标：**名字本身就无歧义**——看到名字就知道是哪一侧、什么粒度。
> 第一原则：全库禁用「会话」一词。它以前同时指平台上的群和 agent 侧的处理过程，是最大歧义来源，已拆成「房间」「轮次」两个词。

## 核心名词

| 术语 | 英文键 | 定义 | 粒度 |
|------|--------|------|------|
| **房间** | room | 平台上一个具体的聊天场所：QQ 群、QQ 私聊、Discord 频道、KOOK 频道。标识 = （平台，房间号） | 平台侧 |
| **账号** | account | 平台侧登录的机器人身份（QQ 号、Discord bot）。一个账号连一个平台 | 平台侧 |
| **设备** | device | 一个**虚拟**实体：订阅若干房间，有一个人格、一份记忆、一个串行处理队列。与硬件无关 | 两侧之间 |
| **订阅** | subscription | 设备对某个房间的一条长期关注关系。一张订阅 = 一个房间 + 三条**策略**：接收策略（收哪些消息）、发送策略（用哪个账号发）、唤醒策略（什么时候叫醒）。三条策略都**可被用户换成自己的逻辑**（来源：用户裁定） | 两侧之间 |
| **人格** | persona | 设备说话的性格设定文本 | 设备 |
| **记忆** | memory | 设备的长期记忆，由 harness 侧持有；桥只按名字引用，名字同时是串行队列的键 | 设备 |
| **轮次** | turn | 设备被叫醒后的一次完整处理：收未读 → agent 干活 → 回复 → 收工。同一设备的轮次严格串行 | 设备 |

## 消息与记录

| 术语 | 英文键 | 定义 |
|------|--------|------|
| **内容元素** | element | 消息的最小组成单位。核心定义一套**标准元素表**：text / at / quote（引用）/ image / audio / video / file / 表情。适配器对每个标准元素做最大程度适配；平台不支持时**降级**（如引用降成纯文本）或明确报错，**绝不悄悄丢弃**。平台特有内容装进不透明载荷原样透传（参考 Koishi 的 element 体系与 NoneBot 的 MessageSegment，不是 OneBot 专属概念；来源：用户裁定要跨平台中立） |
| **策略** | policy | 一段决定行为的逻辑，有默认实现，也可由用户替换成自己的（内嵌脚本或外置进程）。订阅的三条配置（接收 / 发送 / 唤醒）都是策略 |
| **流水** | transcript | 房间的完整消息日志，投没投过都在。投递不改流水，只推水位 |
| **未读** | unread | 某个房间自上次投递之后新进来的消息，按房间各自累积 |
| **水位** | watermark | 「某个设备在某个房间里处理到哪条了」的游标，粒度是**设备 × 房间**；只经 AI 显式确认（`ack_messages`）前推，未确认的留在未读、下轮重投（见 ADR-0010）。自己发的消息永不算未读 |
| **笔记** | note | 设备在某个房间里的速记事实（术语 / 成员 / 话题），按房间隔离，跨平台不串 |
| **平台事件** | platform event | 房间里发生的非消息事情：拍一拍、成员变动、频道创建。默认记录进流水，只对订阅的房间记 |

## 机制

| 术语 | 英文键 | 定义 |
|------|--------|------|
| **唤醒策略** | wake policy | 每条订阅各自配置的「什么时候叫醒设备」。默认策略：**@ 我就醒 + 叫昵称就醒 + 攒够 N 条就醒 + 被拍（poke）就醒**（来源：用户裁定）；其它事件类型匹配默认关。只管叫不叫醒，不管记不记录 |
| **时钟策略** | clock policy | 按时间触发的评估：固定间隔或房间空闲超时后检查「有没有未处理完的、要不要主动说话」，需要就开一轮。默认关闭、按订阅开启（见 ADR-0011） |
| **适配器** | adapter | 一种平台协议的实现（OneBot 11、Satori、将来的 Discord / KOOK 直连）。职责：把平台帧解成事件、把动作编成平台帧 |
| **harness 适配器** | harness adapter | 和上面那个不是一回事：桥**外面**那一半，活在 harness 里。干两件事——把桥的工具挂进 harness（工具面），把推来的一轮变成 harness 里的一次对话并知道什么时候结束（轮次驱动）。这两件事可以分开缺席（见 [06](06-harness-adapters.md)） |
| **harness** | harness | 承载 agent 的运行环境（DSH、WorkBuddy、Trae、Codex……）。桥不实现 agent，只接 harness |
| **接入点** | endpoint | harness 连接桥的通道（本机套接字 / TCP + 接入令牌） |
| **接入令牌** | token | 每个设备一把。harness 握手时出示，令牌对上哪个设备，那条连接就绑到哪个设备；令牌不对直接断开 |

## 工具面

来源：用户裁定——不止有 send，还要有 get 等读取类工具。下表是提案，等用户圈定第一版范围。

| 工具 | 参数 | 行为 |
|------|------|------|
| `send_message` | elements | 发到**当前轮次**的房间 |
| `send_message_to` | elements, to | 发到别的房间；`to` 的可选目标 = 该设备的全部订阅，越界拒绝 |
| `get_history` | room, before, limit | 查房间的流水（读自己订阅的房间） |
| `list_rooms` | — | 列出本设备订阅了哪些房间（发 `send_message_to` 前知道自己能选哪） |
| `get_notes` | room | 读设备在某个房间的笔记 |
| `set_note` | room, key, value | 写一条笔记 |
| `del_note` | room, key | 删一条笔记 |
| `get_platform_events` | room, limit | 查最近记录的平台事件 |
| `wait_message` | room, timeout | 阻塞等该房间的新未读，等到作为结果返回并自动确认；超时返回空 |
| `ack_messages` | ids | 确认消息处理完毕，水位前推；未确认的下轮重投 |

## 旧词 → 新词对照

| 旧词 | 新词 | 为什么改 |
|------|------|----------|
| 会话（平台侧） | 房间 | 「会话」两侧混用，歧义之源 |
| 会话 / agent 侧会话 | 轮次（一次处理）/ 设备（持续实体） | 拆开两个不同粒度 |
| 归档 | 流水 | 「归档」像动作，「流水」像东西本身 |
| 范围（scope） | 订阅（subscription） | 「范围」看不出是有主物的；订阅一眼看出属于哪个设备 |
| ConversationKey | 房间标识（RoomId） | 跟着「房间」走 |
| 群（group 字段） | 房间 | 不再预设 QQ 语义 |

## 命名时严格遵守

1. 平台侧的东西一律不带 agent 色彩；agent 侧的东西一律不带平台色彩。
2. 每个名词定义里写清粒度（哪一侧、属于谁）。
3. 新概念入库前先过一遍本表：能不能用已有名词表达？不能才新增，并补进本表。
